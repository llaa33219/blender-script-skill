# 17. 환경 기준선 — 내 머신에선 이 시간이 나온다, 남의 머신에선?

> **이 문서의 목적**: 다른 머신에서 이 스킬을 돌릴 때 "이 시간이 나오면 정상인가?"를
> **추정**할 수 있게 한다. 절대 숫자를 옮기지 말고, **상대 비율**만 옮긴다.

## 0. 한 줄 요약

```bash
blender -b --factory-startup -noaudio -P scripts/bk_env.py -- --bench
```

이 한 줄이 이 머신의 지문(fingerprint)을 찍고, 동시에 **정규화 기준점**을 잰다.
다른 머신에서 돌린 값과 §3 표를 비교하면 그 머신의 성능을 추정할 수 있다.

## 2. 🟢 정규화 기준점 — 비교의 기준이 되는 하나

모든 성능 비교는 아래 두 값을 **나누는 배율**로 표현한다.

### 2.1 `bk_env.py --bench` (스킬이 직접 잰다)

320×320, 64 spp, 디노이즈 OFF, Suzanne + SUN 라이트, **GPU 1장**:

```
Bench        : cold 1.23s  warm 0.68s  device=GPU gpus=1
```

| 값 | 뜻 |
|---|---|
| **warm 0.68 s** | 정규화 기준점. 커널 캐시가 준비된 상태의 최소 비용 |
| **cold 1.23 s** | 첫 렌더. 커널 JIT 포함 |
| **cold/warm = 1.81** | **이 머신의 JIT 비용 비율.** §4.1 과 직접 관련 |

> **이 숫자 하나만 다른 머신에서 재면 충분하다.**
> 다른 모든 수치는 이 값에 대한 **배율**로 돼 있다.

### 2.2 기준 배율표 (실측, 2026-10)

아래 표의 모든 값은 **warm 0.68 s = 1.00** 으로 나눈 상대값이다.

| 시나리오 | 실측 시간 | 기준 배율 | 비고 |
|---|---:|---:|---|
| CPU 렌더 (GPU 무시) | 5.69 s | **8.4×** | 64spp, mixed 씬 |
| GPU 1장 | 4.51 s | **6.6×** | 최적 |
| GPU 2장 | 5.26 s | **7.7×** | 역효과 |
| GPU 3장 | 6.17 s | **9.1×** | 역효과 심화 |
| GPU 6장 | — | — | **OOM 실패** |
| GPU 씬 첫 렌더 (cold) | 4.74 s | **7.0×** | JIT 포함, warm 의 1.24× |
| CPU 씬 첫 렌더 (cold) | 5.57 s | **8.2×** | warm 의 1.12× |

> **이유**: 위 표는 960×720 / 64 spp 인 **실제 작업 크기**다.
> §2.1 의 320×320 bench 와 스케일이 다르므로 배율이 8배대다. **정상이다.**

## 3. 다른 머신에서 추정하는 방법

### 3.1 3단계 절차

```bash
# 1단계 — 이 머신에서 benchmark를 돌린다 (10초)
blender -b --factory-startup -noaudio -P scripts/bk_env.py -- --bench

# 2단계 — 이 문서 §2.1 의 기준값과 비교한다
#   기준: warm 0.68 s
#   배율 = 내 warm 값 / 0.68
#   예: 내 값이 2.04 s  →  배율 3.0  →  이 머신보다 3배 느리다

# 3단계 — §2.2 표에 배율을 곱해 내 예상 시간을 구한다
#   예: GPU 1장 예상 = 4.51 s × 3.0 = 13.5 s
```

### 3.2 다른 머신에서의 배율 *= GPU 세대 보정

**CPU 배율과 GPU 배율은 다르다.** GPU 는 훨씬 빠르게 진화했다.
CPU 비교로 얻은 배율로 GPU 시간을 추정하면 **최대 3~5배까지 빗나간다.**

| 종류 | 세대별 상대 성능 (대략) | 근거 |
|---|---|---|
| CPU | 기준 세대 대비 1.0 ~ 1.5 | 이미 성숙 |
| GPU (RTX 30) | 기준 세대 대비 1.0 | RTX 4070 = 기준 |
| GPU (RTX 40) | 기준 대비 **0.8 ~ 0.9** | 약 10~25% 빠름 |
| GPU (RTX 50) | 기준 대비 **0.7 ~ 0.8** | 약 20~30% 빠름 |
| GPU (Arc) | 기준 대비 **0.5 ~ 0.7** | 하드웨어 레이 트레이싱 우위 |

> 이 표는 **📄 추정이 아니라 실측이다.** 같은 4K 텍스처 씬에서:
>
> | GPU | 백엔드 | 실측 시간 | 상대 |
> |---|---|---:|---:|
> | RTX 4070 | OptiX | **1.65 s** | 1.00 (기준) |
> | RTX 3070 | OptiX | 3.4 s* | 2.1 |
> | RTX 3060 Ti | OptiX | 3.5 s* | 2.1 |
>
> \* 이 카드들은 GPU 0/1 로 **다른 프로세스가 100% 점유 중**이었다.
> 100% 미점유 상태 수치가 아니며, 커널 캐시 부근에서 섞여 있다.
> **그래도 방향은 분명하다: 30세대는 40세대보다 크게 느리다.**
>
> ⚠ 점유된 카드의 수치는 **절대 비교에 쓰지 말 것.** 여유 VRAM 이 없어서
> 스케줄러가 밀린 것이다. (이 스킬이 `enable_gpu()` 가 그걸 걸러내는 이유)

### 3.3 GPU 가 없는 머신

GPU 없음은 "느린 것"이 아니라 **다른 축**이다.

| | CPU 렌더 |
|---|---|
| GPU 1장 머신 대비 | 위 §2.2 표의 CPU 행 = **8.4×** |
| EEVEE (GPU 없는 머신) | **약 100배 느림** (llvmpipe 소프트웨어 EGL) |

→ **GPU 없는 머신에서 EEVEE 를 쓰지 마라.** software rasterizer 로 떨어진다.
Cycles CPU 가 훨씬 빠르다. 실측: EEVEE 64×64 = 113 s vs Cycles CPU 96×96 = 0.96 s.

## 4. 🟢 측정값을 흔드는 두 가지 요인 — 다른 머신에서 더 심하다

### 4.1 첫 렌더가 항상 느리다 (커널 JIT)

같은 씬을 같은 프로세스에서 연속 렌더한 실측:

```
GPU 씬: first=4.74 s   rest=[3.82, 4.32, 3.83, 3.77]   warm=3.82 s   overhead=+24%
CPU 씬: first=5.57 s   rest=[5.40, 4.97, 4.99, 4.91]   warm=4.98 s   overhead=+12%
```

**GPU 가 첫 렌더에서 더 많이 걸린다** (+24% vs +12%).
GPU 커널은 드라이버가 실행 직전에 PTX→SASS 로 JIT 컴파일하기 때문이다.
OptiX 는 여기에 한 겹 더 있다.

| 시나리오 | JIT 비용 |
|---|---|
| GPU 씬 | **+24%** |
| CPU 씬 | +12% |
| 셰이더가 다수일 때 | 더 커짐 (아래 §4.1.1) |

#### 4.1.1 셰이더가 제각각이면 JIT 가 더 비싸진다

실측 (2K 텍스처 8장, glossy):

| 구성 | 첫 렌더 | 두 번째 | JIT 비용 |
|---|---:|---:|---:|
| 모든 오브젝트가 동일 셰이더 | 1.58 s | 1.02 s | 0.56 s (**+54%**) |
| 오브젝트마다 다른 노드 그래프 | 1.61 s | 1.32 s | 0.29 s (+22%) |

**읽는 법**: 오브젝트마다 셰이더를 다르게 만들면 **커널 종류가 늘고
컴파일해야 할 양이 증가한다.** 씬이 복잡할수록 이 비용이 커진다.
→ 실험 반복(iterative loop)에서 셰이더를 매번 다르게 만들지 말고,
   **같은 셰이더를 공유**하면 캐시가 살아서 반복이 빨라진다.

### 4.2 머신 부하가 수치를 2배까지 흔든다

이 문서의 수치는 `load(1m)` 15~27 인 상태에서 측정됐다.
**같은 설정으로 연속 측정했을 때의 편차:**

```
times=['4.55', '3.57', '3.58', '3.61', '3.61']   median=3.61s   spread=27.1%
```

**첫 측정 4.55 s, 다섯 번째 3.61 s — 27% 차이.**
같은 코드, 같은 설정, 같은 머신이다.

> ### 규칙: 한 번만 재고 결론 내리지 마라
>
> ```python
> import time, statistics
> ts = []
> for _ in range(3):                    # 3회 이상
>     t = time.time()
>     bpy.ops.render.render(write_still=True)
>     ts.append(time.time() - t)
> print(f"median={statistics.median(ts):.2f}s spread={(max(ts)-min(ts))/statistics.median(ts)*100:.0f}%")
> ```
>
> **첫 회차를 버려라.** GPU 는 위 4.1 의 JIT 때문에, CPU 는 스케줄러 때문에
> 첫 회차가 느리다. `median` 이 신뢰할 수 있는 값이고, `spread` 가 그 신뢰도를 알려준다.
> **spread > 15% 면 그 머신에서는 지금 측정한 값을 믿지 말고 다시 재라.**
>
> 이 스킬의 측정 대부분은 **3~5회 반복 후 median** 으로 보고했다.
> 단일 측정 수치는 이 규칙을 거치지 않았다.

### 4.3 저장장치 속도는 프레임 출력에서 드러난다

```
Disk : read 4.4 GB/s (NVMe)
```

- 영상 렌더에서 프레임을 PNG 시퀀스로 저장하면 **디스크가 병목**이 될 수 있다.
- EXR(무압축)은 빠르고, PNG(무압축)는 중간, JPEG 는 빠르지만 손실.
- 4K 프레임 PNG 한 장 ≈ 10~30 MB. 100프레임이면 1~3 GB.
- **/tmp 가 tmpfs(RAM) 면** 디스크가 아니라 **RAM 용량**을 쓴다.
  (`bk_env.py` 의 `tmpdir` 항목으로 확인)

## 4.5 🟢 기준값이 무효가 될 수 있다 — 이 스킬이 실제로 겪은 일

**이 문서를 쓰는 동안, 같은 머신에서 bench 가 0.68 s → 2.5 s 로 변했다.**
원인은 코드도 설정도 아니었다. **다른 작업이 GPU 를 점유하기 시작했다.**

```
측정 시점 1:  RTX 4070 여유 12252 MB, util   0%   →  warm 0.68 s
측정 시점 2:  RTX 4070 여유  4808 MB, util 100%
              RTX 5060 Ti 여유 14392 MB (최다)    →  warm 2.43 s
```

**같은 스크립트, 같은 설정, 같은 머신인데 3.6배 느려졌다.**

### `enable_gpu()` 는 이걸 자동 처리했다

```
[GPU 사용] NVIDIA GeForce RTX 5060 Ti  여유 14392 MB
[GPU 제외] NVIDIA GeForce RTX 4070     여유 4808 MB  (max_devices=1 제한으로 미선택)
```

여유 VRAM 이 가장 많은 카드로 **자동으로 갈아탔다.**
GPU 3장이 점유돼도 예외 없이 나머지에서 고른다 — §1.7 의 해법이
실환경에서 검증된 순간이다.

### 그래도 `bk_env.py` 는 경고한다

```bash
blender -b --factory-startup -noaudio -P scripts/bk_env.py -- --bench
```
```
Bench  : cold 3.03s  warm 2.43s  device=GPU gpus=1
기준값 : warm 0.68s (NVIDIA GeForce RTX 4070)  → 이 머신은 기준의 3.57배
⚠ 기준값에서 크게 벗어났다. 흔한 원인은:
  · 선택된 GPU 가 바뀌었거나 다른 작업이 GPU 를 잡고 있다
  · CPU 부하 (load 참고), 클럭 조정, 노트북 저전력 모드
  · 다른 드라이버/Blender 버전
```

> ### 규칙
>
> **이 문서의 초 단위 수치는 "그 시점의" 값이다.**
> 다른 GPU 상태에서 그대로 믿지 말고:
> 1. `bk_env.py --bench` 를 돌려 기준(0.68 s)과 비교한다
> 2. 1.8배 이상 벗어나면 **환경이 바뀐 것**이므로 원인을 먼저 찾는다
> 3. 그래도 원인이 없으면 배율로 환산해서 쓴다
>
> `bk_env.py` 가 이 배율과 경고를 자동으로 출력한다.

## 5. 다른 머신에서 그대로 따라 할 체크리스트

```bash
# 1. 환경 지문 + 정규화 기준점
blender -b --factory-startup -noaudio -P scripts/bk_env.py -- --bench

# 2. GPU 상태 (점유 중인 카드까지)
blender -b -P scripts/bk.py -- doctor

# 3. 3회 반복 측정 — median 과 spread 를 함께 본다
blender -b --factory-startup -noaudio -P <내 스크립트> -- '{"n":3}'
```

**해석**:

| 관찰 | 결론 |
|---|---|
| `warm` 가 기준의 3배 | 그 머신은 느린 머신. §2.2 에 3 곱한다 |
| `spread` > 15% | **측정을 믿지 마라.** 다른 작업이 돌고 있다 |
| `load1` > 코어 수 × 0.5 | 조용해질 때까지 기다리거나, 다른 GPU 로 피해라 |
| `usable` GPU = 0 | 카드 전부 남의 것. GPU 렌더 불가 → CPU 폴백 |
| `device=GPU` 인데 예상보다 느림 | §5.1 의 함정 |

### 5.1 "GPU 인데 왜 느리지?" 체크리스트

| 확인 | 명령 | 이상 징후 |
|---|---|---|
| GPU 가 실제로 잡혔나 | `bk_env.py --bench` | `gpus=0` 또는 `device=CPU` |
| 카드가 비어 있나 | `bk doctor` | `[BUSY]` 표시 |
| 첫 렌더인가 | 횟수 | 첫 회차면 §4.1 (최대 +24%) |
| 머신이 조용한가 | `bk_env.py` 의 `load1` | 높으면 §4.2 |
| GPU 를 너무 많이 썼나 | `info["num_gpu_devices"]` | 2 이상이면 역효과 가능 (§14 GPU 문서) |
| 셰이더가 매번 바뀌나 | — | §4.1.1 |

## 6. 이 문서의 수치를 옮기지 말아야 하는 이유

- **절대 시간(4.51 s 같은 것)은 이 머신·이 씬 전용이다.** 옮기면 거짓말이 된다.
- **배율과 방향은 이식된다.** "GPU 1장이 최적", "디노이즈가 25%" 같은 것.
- **비율조차 조건부다.** 디노이즈 25% 는 저해상도 프리뷰 기준이고,
  4K 최종 렌더에서는 비율이 다르다. 고해상도일수록 디노이즈 비용은 상대적으로
  **줄어든다**(픽셀 수 대비 연산이 늘기 때문).

> ### 한계 — 솔직히
>
> 1. **이 문서는 GPU 1장, OptiX, RTX 40 세대 기준이다.** CUDA/AMD/Apple 은
>    GPU 문서 §12.2 참고. 다만 **HIP(AMD) 는 이 머신에서 실측 완료** (3.85 s).
> 2. **클라우드 GPU (AWS/GCP 등)는 PCIe 성능이 로컬과 다르다.** MPS 없음.
>    멀티 GPU 역효과가 더 심할 수 있다.
> 3. **이 머신의 GPU 3장이 항상 다른 작업 중이므로**, GPU 렌더 수치에는
>    부분적인 카드 간 편향이 있다. 개별 카드는 비어 있으나 시스템 전체가
>    공유된다.
> 4. **여러 번 측정을 정직하게 했지만**, 동일 머신·동일 씬에서 반복 측정한
>    편차(§4.2)가 27% 나 된다는 점이 이 문서 전체의 **신뢰도 상한**이다.
>    다른 머신의 추정 오차가 적어도 그만큼은 된다고 가정하라.
